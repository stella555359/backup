# 5G gNB 系统测试与自动化回归建设

## 一句话定位

面向 5G 基站核心特性，负责系统集成测试、Robot Framework 自动化用例开发、公共关键字建设和多 release 自动回归保障。

## 背景与痛点

5G gNB 特性涉及 SA/NSA、多 CA 组合、切换、SRS 波束赋形、上行 MIMO 等复杂场景，测试环境多、参数多、版本迭代快。人工回归效率低，跨 release 维护成本高，需要通过自动化用例、公共关键字和 Jenkins 回归体系提升稳定性。

## 我的职责

- 参与需求评审，制定测试策略和测试计划。
- 独立搭建端到端测试环境，包括 BBU、RRU、AMF、Android 终端和衰减器等。
- 使用 Wireshark、TTI Trace、BIP 和日志进行分层问题定位。
- 基于 Robot Framework + Python 开发公共关键字和自动化用例。
- 负责 CIT、CRT、CDRT 等不同回归级别的用例维护和失败分析。
- 参与组内 Code Review，并对接 TAF 库接口变化。

## 核心流程

```text
需求评审
-> 测试策略和场景设计
-> 环境搭建
-> 手工验证关键路径
-> Robot 自动化用例开发
-> Jenkins 回归执行
-> 失败分析和 Ticket 跟踪
-> release 适配和复盘
```

## 关键能力

### 自动化关键字抽象

把衰减器控制、基站配置、UE 操作、日志采集、环境检查等动作封装为公共关键字，减少重复代码，让多个 feature 和 release 能复用。

### 分层排障

根据现象判断问题可能属于协议层、调度层、射频层、环境层或自动化脚本层，再结合抓包、Trace、日志和 Jenkins 执行结果定位。

### 多 release 适配

当 TAF 接口、基站配置、测试线环境或 feature 行为变化时，需要评估已有用例影响，更新关键字或用例参数，保证回归集稳定运行。

## 难点与取舍

- 自动化不能只追求覆盖率，还要关注稳定性和维护成本。
- 公共关键字要适度抽象，避免过度封装导致问题定位困难。
- 对新特性先做可行性分析，再决定手工验证、半自动化还是全自动化。

## 面试表达

我在 5G gNB 项目中长期负责系统集成测试和自动化回归建设。我的工作不只是写 Robot 用例，而是从需求评审开始设计测试策略，搭建端到端环境，先验证核心路径，再把稳定流程沉淀成公共关键字和自动化用例。执行阶段通过 Jenkins 做每日回归，对失败用例做分层分析，判断是产品问题、环境问题、脚本问题还是数据问题，并推动 Ticket 闭环。
