## Review: 1 周测试岗面试训练计划

### 整体评价

这份计划结构清晰、日程合理、有真实项目支撑，在**工具链闭环**和 **AI 辅助测试表达**上做得不错。但对照 JD 来看，有几个**关键缺口**会直接影响面试通过率。

---

### 当前计划的优势

1. **7 天渐进式编排**合理，主线 `platform-api → Jenkins → Robot → callback → DB` 是一个完整的项目故事
2. **证据链思维**（接口返回 + 数据库反查 + Jenkins 结果）讲法很好，面试官会认可
3. **AI 辅助测试**部分对齐了 JD 中"AI 测试工具实践"要求，且强调"AI 起草 + 人工复核"的分寸感到位
4. **SQL drill** 10 道面试题 + 10 条 SQL 实战，够用
5. **工具位置图**把 XMind/Postman/JMeter/SQL/AI 嵌入测试全流程讲述，面试时好用

---

### 10 个需要改进的缺口（按优先级排序）

#### 缺口 1（严重）：完全没有信贷业务知识

JD 明确写了 **"负责信贷产品测试，覆盖授信、支用、还款、贷后全流程"**，且 **"消费金融/信贷测试经验优先"**。当前计划零覆盖。

**建议**：Day 1 或 Day 2 加一块 **信贷业务速成**，至少能讲清：
- **授信流程**：用户申请 → 风控审核 → 额度生成
- **支用流程**：额度 → 借款申请 → 放款 → 合同生成
- **还款流程**：正常还款 / 提前还款 / 逾期 / 部分还款
- **贷后管理**：逾期催收、额度调整、结清
- 每个环节的**关键测试点**（状态流转、金额计算、时间节点、并发场景）

这不需要你真的做过信贷系统，但你必须能在面试中**用测试语言讲清楚这四个阶段**。

#### 缺口 2（严重）：项目叙事和 JD 业务方向脱节

你的项目是 CI/CD 测试平台，JD 要的是**信贷产品业务测试**。面试官会问："你做过信贷相关测试吗？"

**建议**：准备一个 **桥接叙事**：
- 先讲你的平台测试经验（接口设计、DB 校验、自动化调度、失败排障）
- 再讲这些能力如何迁移到信贷场景（接口测试 → 授信/放款接口、DB 校验 → 还款金额/状态核对、回调机制 → 异步通知验证）
- 如果有任何金融/支付相关测试经验，一定要准备好讲

#### 缺口 3（中等）：MySQL 知识缺失

JD 写的是 **MySQL**，但当前练习全部基于 SQLite。

**建议**：SQL drill 里补充：
- MySQL 和 SQLite 的主要差异（数据类型、事务、索引）
- `JOIN` 类型面试题（LEFT JOIN / INNER JOIN / 自连接）
- `GROUP BY + HAVING` 组合
- 基本的 `EXPLAIN` 解读
- 事务隔离级别基础概念（面试消金岗常问）

#### 缺口 4（中等）：缺陷管理没有实操

JD 要求 **"缺陷跟踪"**，计划只是概念提及。

**建议**：准备 2-3 个 **bug 报告模板示例**，能讲清：
- 标题写法、严重等级/优先级定义
- 复现步骤 + 期望结果 + 实际结果 + 证据（截图/日志/SQL 结果）
- 缺陷生命周期（新建 → 确认 → 修复 → 验证 → 关闭）
- 用过什么缺陷管理工具（Jira/禅道/Ones 等，至少能讲一个）

#### 缺口 5（中等）：XMind 实际产出为零

JD 列了 **XMind** 作为必要工具。

**建议**：至少产出 **1 张信贷测试脑图**（哪怕用文字结构模拟），覆盖：
- 授信模块测试点（正常/异常/边界）
- 还款模块测试点（正常还款/提前/逾期/部分）
- 面试时能画出来或口述出来

#### 缺口 6（中等）：日志排查没有动手练习

JD 要求 **"能独立排查日志、定位问题"**。

**建议**：Day 4 的排障话术要配合 **真实日志片段**：
- 至少准备 2-3 个典型错误日志场景
- 能演示：看日志 → 定位层级（网络/接口/服务/DB）→ 给出结论
- 结合 platform-api 的 Jenkins console log 和 API error response 做实际练习

#### 缺口 7（低）：冒烟/回归测试策略表达不足

JD 强调 **"把控冒烟/回归测试质量"**。

**建议**：准备标准面试答案：
- 冒烟测试范围怎么定、什么时候执行
- 回归测试策略（全量 vs 重点回归）的判断依据
- 怎么保证回归质量（自动化覆盖率 + 手工补充）

#### 缺口 8（低）：测试报告输出没有覆盖

JD 写了 **"报告输出"**。

**建议**：准备一份测试报告模板的口述：
- 测试范围、用例执行情况、通过率
- 遗留问题和风险
- 上线建议

#### 缺口 9（低）：行为面试 / 软技能准备为零

JD 强调 **"态度端正、执行力强、抗压稳定、对 AI 测试有探索精神、主动好学爱分享"**。

**建议**：用 STAR 法准备 3 个故事：
- 一个体现 **执行力/抗压**（紧急上线、高强度迭代）
- 一个体现 **主动学习**（自学 AI 工具、自动化探索）
- 一个体现 **协作/分享**（推动团队用新工具、做内部分享）

#### 缺口 10（低）：JMeter 性能测试面试话术太薄

**建议**：至少能讲清：
- TPS、响应时间（平均/P95/P99）、错误率
- 聚合报告怎么看
- 什么场景需要性能测试

### 总结

当前计划在**技术工具链**维度做得够用，但在 **业务领域知识（信贷）** 和 **面试软实力表达** 上有明显短板。消金公司招测试工程师，第一轮面试几乎一定会问信贷业务流程和场景设计，如果完全答不上来，工具再熟也很难过。**优先补缺口 1 和缺口 2**。

你的项目里确实用了 Pydantic，只是 Cursor 在帮你搭框架时自动引入的，你没有显式指定过。

**Pydantic 是什么**：FastAPI 的标配搭档，负责做请求/响应的数据校验和序列化。你项目里所有的 `RunCreateRequest`、`RunListResponse`、`RunCallbackRequest` 这些类都继承自 Pydantic 的 `BaseModel`。简单说就是：**API 收到请求时自动校验字段类型和格式，返回响应时自动序列化成 JSON**。

**面试时需要了解到什么程度**：

- 知道它是做数据校验和序列化的
- 知道你的 Request/Response 类都基于它
- 能举例："比如 `RunCreateRequest` 里定义了 `testline` 是 `str` 类型，如果传了数字就会自动返回 422 校验错误"

**简历上要不要写**：两种都行——

- 写 `FastAPI + Pydantic v2` → 显得技术栈更完整，但面试官可能追问细节
- 只写 `FastAPI` → 更安全，因为 Pydantic 是 FastAPI 内置依赖，懂的人自然知道

**建议**：如果你对 Pydantic 的校验机制能讲清楚上面那三点，就保留。如果觉得没把握被追问，改成只写 `FastAPI` 即可。你怎么选？
